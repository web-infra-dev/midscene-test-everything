Midscene Open Device defines an HTTP protocol for discovering devices, acquiring control, capturing screen images, and executing input actions. This draft describes version 1 of the protocol.

This is a Midscene project RFC. Draft means its contract is still under review. The endpoint descriptions below document the current shared Open Device implementation; unresolved extensions are listed separately.

Introduction

A device service connects a client to hardware such as an iPhone or a robot-controlled touchscreen. The service handles hardware setup and calibration before exposing devices through the protocol.

Midscene Agent performs model inference and task planning. The device client manages authentication and session renewal. Playground displays preview frames and sends explicit input actions. The service owns device readiness, resource exclusion, image capture and hardware execution.

Open Device defines one API contract with multiple implementations. Robot arm and Mac Bluetooth HID services implement that contract today. An ESP32-based service or another backend could implement the same API, allowing Midscene clients to use it through the same device access flow. Each implementation advertises its supported actions and preview capabilities.

The API layer in the figure represents the shared protocol, not a required central gateway. Clients connect to the chosen implementation's service address. Hardware reports, robot units and camera calibration remain private to that implementation. Installation, pairing, calibration, model credentials and task scheduling are outside this protocol.

Conformance

This document defines requirements for Midscene device services and clients. “MUST” denotes a requirement, “SHOULD” a recommendation with possible justified exceptions, and “MAY” an optional behavior.

Diagrams, examples, notes and open questions are informative. Request fields, response fields and processing steps describe the version 1 contract. Algorithms may be implemented differently if their externally observable results are equivalent.

A service MUST enforce session ownership of the control resource and validate actions before execution. A client MUST authenticate requests, use an active session and select actions supported by the target device.

Implementation note. Draft status means this contract is under review. It does not claim a separate certification process or that unresolved extensions are already implemented.

Terminology

Device
A configured target identified by a service-scoped ID.
Control session
A time-limited reservation through which a client captures images and sends actions to one device.
Control resource
The exclusive hardware resource used by a session. A phone normally owns one resource; several screens can share one robot arm.
Client
A Midscene SDK or Playground connection to a service.

Transport and Authentication

Protocol endpoints are under /api/v1/. A client sends the service credential in the Authorization: Bearer <token> header. Requests with a JSON body use application/json. Responses use JSON unless the endpoint returns a preview stream.

IDs are opaque strings scoped to a service. Clients must URL-encode session IDs in paths. A session ID does not replace the service token: every session request also requires authentication. The current token grants service access; it does not identify an individual user.

Session and action bodies reject unknown fields. The shared handler limits JSON request bodies to 32 KiB and returns 413 for larger bodies. Do not put credentials in query strings or examples.

Device Discovery

GET /api/v1/devices returns an object with a devices array. Each entry contains an ID, name, status and a list of supported action types. Status is available, busy, or offline. A device can advertise preview: "mjpeg" when it supports live preview.

{
  "devices": [{
    "id": "phone-1",
    "name": "Test iPhone",
    "status": "available",
    "screenSource": "camera",
    "actions": ["tap", "swipe"],
    "preview": "mjpeg"
  }]
}
FieldMeaning
id, nameRequired device ID and display name. Names need not be unique.
statusavailable: ready to acquire; busy: control resource reserved; offline: not ready for control.
actionsRequired list of supported action types; support is device-specific.
screenSourceOptional capture source: usb, camera or airplay.
previewOptional live-preview capability; currently mjpeg.
inputGuidanceOptional backend guidance for the client’s input behavior.

Discovery is a snapshot, not a reservation. Another client may acquire the resource before this client requests a session. The acquisition response is authoritative. Clients must not silently select a different device after an acquisition failure.

Control Sessions

Method and pathResult
POST /api/v1/sessionsAcquire control using a deviceId. A 201 response contains id, deviceId, and expiresInMs.
POST /api/v1/sessions/{id}/heartbeatRenew the session lease.
DELETE /api/v1/sessions/{id}Release control. An already-released ID also returns 200.

A service reserves the underlying control resource exclusively. Several screens served by one robot arm can share that resource. The current lease duration is 30 seconds. A client renews it by sending a heartbeat before expiry.

Acquisition and renewal

POST /api/v1/sessions
Authorization: Bearer <token>
Content-Type: application/json

{"deviceId":"phone-1"}

HTTP/1.1 201 Created
Content-Type: application/json

{"id":"session-1","deviceId":"phone-1","expiresInMs":30000}

deviceId must contain 1–128 characters. There is no waiting queue or forced takeover. Unknown, unready and occupied devices return 409. Two screens sharing a robot arm cannot acquire independent control sessions at the same time.

A successful heartbeat returns 200 {} and resets the lease from the time the service handles it. The current SDK sends heartbeats at approximately five-second intervals. Clients should use the returned expiresInMs and renew well before expiry. Screenshots, actions and preview traffic do not renew the lease. Heartbeats must continue while an action is running.

New Session processing steps

  1. Parse the request body and validate deviceId. Reject malformed input with 400.
  2. If the service is stopping or holding an update reservation, return 503.
  3. If the target is occupied, unavailable or disconnected, return 409.
  4. Resolve its control resource. If that resource is occupied, return 409.
  5. Create an opaque session ID, reserve the resource and start its lease.
  6. Return 201 with id, deviceId and expiresInMs.

Ending a session

Release aborts the session lifetime, requests cancellation of its action and closes preview streams. The resource remains reserved until the running action settles. Cancellation cannot undo physical input already sent. A backend may remain unavailable after release.

DELETE /api/v1/sessions/{id} returns 200 {} after release, including for an unknown or already-released ID. Other requests using an unknown, expired or closing session receive 410. A heartbeat cannot revive an expired session.

Sessions are held in memory and do not survive a service restart. Reconnecting requires a new acquisition. Interrupted tasks and actions are not replayed automatically.

Screen Capture and Preview

GET /api/v1/sessions/{id}/screenshot returns a base64 JPEG in jpeg, along with width, height, sequence, and receivedAt.

GET /api/v1/sessions/{id}/preview streams JPEG frames as multipart/x-mixed-replace when the device supports preview.

Screenshot response

{
  "jpeg": "<base64-encoded JPEG bytes>",
  "width": 430,
  "height": 932,
  "sequence": 42,
  "receivedAt": 1794441600000
}

jpeg contains base64 bytes without a data-URL prefix. Width and height describe the returned image in pixels. Sequence is a backend frame identifier, not a globally unique ID. receivedAt records frame receipt time as Unix epoch milliseconds; it is not a guarantee of the physical exposure time or client-clock synchronization.

Capture freshness depends on the backend. This endpoint does not promise that the frame was exposed after the preceding action finished. Agent must observe the resulting UI rather than assume that action success means rendering has settled.

Live preview

Content-Type: multipart/x-mixed-replace; boundary=midscene-frame
Cache-Control: no-store, no-transform

--midscene-frame
Content-Type: image/jpeg
Content-Length: <JPEG byte length>

<binary JPEG bytes>

Parse the boundary from the response header. Each part contains a JPEG. The stream is for live observation, not a lossless recording. The current implementation samples at up to about 10 frames per second, skips duplicate sequences and skips writes to clients under backpressure. Frame rate and delivery of every captured frame are not guaranteed.

Preview readers are shared within a session. Closing the last preview subscriber releases its reader without releasing control. Ending the session closes all its preview connections. A broken preview connection alone does not prove that the session ended; reconnect only while the session remains valid. A device without preview support returns 404.

Actions

Coordinate Space

Points are expressed in the pixel coordinates of the device screenshot, with the origin at the top left. A client using a resized preview converts its coordinates to screenshot coordinates before sending an action.

X increases to the right and Y increases downward. Coordinates refer to the corrected screenshot, not the raw camera sensor, browser CSS pixels or robot coordinates. The service maps them to its hardware.

For a displayed image rectangle with origin (left, top) and size (displayWidth, displayHeight):

x = (pointerX - left) × screenshotWidth / displayWidth
y = (pointerY - top) × screenshotHeight / displayHeight

Use the image rectangle, excluding letterboxing. Preview and screenshot must represent the same crop and orientation for this conversion. Re-read image dimensions after a capture configuration change.

The shared schema accepts finite numbers, including fractions; it does not enforce image bounds or normalize to percentages. Clients should send points inside the screenshot. Backend handling of out-of-bounds points is not a portable contract.

Perform an Action

POST /api/v1/sessions/{id}/actions accepts one action object. Its type identifies the action. A client selects an action from the device's advertised list.

{
  "type": "tap",
  "point": { "x": 120, "y": 300 }
}

The service validates the request and checks the session and action capability. It returns 409 if another action is in progress in the same session. It returns 200 with {} after the device backend completes the action and the session is still active.

The service processes an action as follows:

  1. Require an active session; otherwise return 410.
  2. Read and validate the action body; return 400 for invalid input, or 413 if it exceeds the body limit.
  3. Recheck the session after reading the body.
  4. When the backend supplies a capability list, reject an action absent from it with 422.
  5. If an action is already running in the session, return 409.
  6. Execute the action with cancellation linked to the session lifetime and request connection.
  7. After successful execution, recheck the session and return 200 {}. Clear the in-flight action state on success or failure.
TypeAdditional fieldsIntent
tappointTap one location.
doubleTappointTap twice at the same point as one action.
scrolldirection (up or down), optional steps (1–24) and pointScroll vertically. The visible distance per step depends on the device.
longPresspoint, optional durationMsPress and hold.
swipefrom, to, optional durationMsSwipe between two locations.
dragAndDropfrom, to, optional durationMsDrag between two locations.
typeTexttext, optional replaceEnter text in the focused input.
keykeySend a backend-supported key.
home, back, clearInputNoneNavigate or clear the focused input.

Every point has exactly x and y. Optional durations range from 0 to 5000 milliseconds; omitted durations use the backend default. Text is limited to 8192 JavaScript string code units; key names contain 1–128. Key vocabulary and precise gesture timing are backend-specific. Advertising a type does not imply identical hardware timing across backends.

Clients serialize actions themselves: the service rejects concurrent actions with 409 rather than queuing them. Heartbeats and preview can continue during execution. A successful action response means the backend finished its execution procedure, not that the app reached the requested business outcome.

If an action connection closes, the service signals cancellation to the backend. Already-performed input may have taken effect. A timeout, dropped response or error after execution leaves the outcome uncertain; clients must not automatically replay the action. Obtain a new screenshot and decide how to proceed.

Errors

JSON errors contain an error message. Clients use HTTP status codes to distinguish failure cases.

  • 400 for invalid request data.
  • 401 for a missing or invalid service token.
  • 404 for an unknown route or unavailable preview.
  • 409 for a busy or unavailable device, or a backend conflict.
  • 410 for a session that is no longer active.
  • 413 for a session or action body exceeding 32 KiB.
  • 422 for an unsupported action type.
  • 503 for a service that is unavailable to new requests.
HTTP/1.1 410 Gone
Content-Type: application/json

{"error":"Device control session has ended."}

The message above is illustrative. Error wording and language are not stable identifiers. The current protocol has no machine-readable error subcode, so 409 alone cannot distinguish resource contention from a backend execution failure.

On 401, correct the credential. On 410, stop using that session and acquire again explicitly. For acquisition 409, refresh device state or wait for the current owner. For action failures, inspect device state before deciding whether to issue another action. Once preview headers have been sent, an error ends the stream instead of inserting a JSON error into JPEG data.

Complete interaction

All abbreviated session paths above retain the /api/v1 prefix and the Authorization header. Clients should release in a cleanup handler even when task execution fails. Lease expiry is the fallback if the client can no longer contact the service.

Versioning and compatibility

/api/v1 identifies the wire protocol version. It is distinct from the npm package version and OpenAPI document metadata. Clients should ignore additional response fields and use advertised capabilities instead of assuming every service supports every action.

The RFC describes behavioral semantics. OpenAPI describes HTTP shapes; shared types, validators and service tests implement the contract. Changes should keep those artifacts consistent. The current OpenAPI action schema is less detailed than the runtime validator; the action table above records the accepted fields.

Open questions

The following are unresolved extensions, not existing guarantees:

  • Stable error subcodes for busy, offline and backend execution failures.
  • A shared key-name vocabulary and richer per-action capability limits.
  • A frame or coordinate-space revision to detect stale coordinates after rotation or recalibration.
  • Request identifiers and action-result lookup for uncertain network outcomes.
